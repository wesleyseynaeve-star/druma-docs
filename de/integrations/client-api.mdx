Die Client-API-Integration (CAPI) schafft einen direkten Datenkanal zwischen einem bestimmten Kunden und Ihrem Druma-Konto. Sie hat zwei unabhängige Hälften:

- **Eingehend**: Das System des Kunden sendet Aufträge automatisch an Druma. Keine manuelle Auftragseingabe nötig.
- **Ausgehend**: Druma sendet Statusereignisse (abgefahren, geliefert, abgerechnet usw.) in Echtzeit an das System des Kunden.

Sie können jede Hälfte unabhängig aktivieren, oder beide zusammen. Jeder Kunde erhält sein eigenes Token und seinen eigenen Endpunkt, sodass Zugangsdaten vollständig isoliert sind.

---

## Wann Sie dies nutzen

CAPI ist sinnvoll, wenn ein Kunde:

- Ein WMS-, ERP- oder Auftragsverwaltungssystem hat, das HTTP-Aufrufe machen kann
- Häufig Sendungen bucht und die Anmeldung in Ihrem Kundenportal für die Auftragserstellung vermeiden möchte
- Automatisierte Lieferbestätigungen an sein System für nachgelagerte Abläufe benötigt (Lagerbuchung, Rechnungsstellung, Bestandsaktualisierung)

Für Kunden, die gelegentlich buchen oder das Portal bevorzugen, fügt CAPI unnötige Komplexität hinzu. Nutzen Sie stattdessen das Standard-Kundenportal.

---

## Wo Sie die Einstellungen finden

1. Gehen Sie im linken Menü zu **Kunden**.
2. Öffnen Sie den Kundendatensatz.
3. Klicken Sie auf den Tab **API**.

Sowohl eingehende als auch ausgehende Einstellungen befinden sich auf diesem Tab.

---

## Eingehend — der Kunde sendet Aufträge an Druma

<Steps>
  <Step title="Eingehend aktivieren">
    Aktivieren Sie im Tab **API** den Schalter **Eingehende API aktivieren**.
  </Step>
  <Step title="Ein Token generieren">
    Klicken Sie auf **Token generieren**. Das vollständige Token wird **einmalig** angezeigt — kopieren Sie es sofort und speichern Sie es sicher (ein Passwort-Manager eignet sich gut). Druma speichert nur einen Hash des Tokens; der vollständige Wert ist nicht wiederherstellbar. Nach diesem Bildschirm werden nur die ersten 20 Zeichen als Referenz angezeigt.
  </Step>
  <Step title="Die Endpunkt-URL teilen">
    Kopieren Sie die unter dem Token-Feld angezeigte **Endpunkt-URL**. Geben Sie diese URL und das Token an das technische Team des Kunden.
  </Step>
  <Step title="Feldzuordnungen konfigurieren (optional)">
    Verwendet das System des Kunden andere Feldnamen als Druma (z. B. `shipment_id` statt `reference`), fügen Sie Zeilen zur Tabelle **Feldzuordnung** hinzu, indem Sie auf **+ Zuordnung hinzufügen** klicken. Jede Zeile ordnet einen Feldnamen des Kunden (linke Spalte) dem entsprechenden Druma-Feldnamen (rechte Spalte) zu.
  </Step>
</Steps>

Das System des Kunden sendet eine `POST`-Anfrage an die Endpunkt-URL mit dem Header `Authorization: Bearer <token>` und einem JSON-Body. Druma erstellt den Auftrag im Status **Entwurf** mit dem Quellkennzeichen `booked_via: client_api`. Ein Planer kann Auftragsentwürfe von der Planungstafel aus prüfen und bestätigen.

<Note>
Über CAPI erstellte Aufträge kommen als Entwürfe an. Sie erscheinen erst als zugewiesen auf der Tafel, wenn ein Planer (oder eine Automatisierungsregel, falls konfiguriert) sie zum nächsten Status bewegt. Das ist Absicht — es erlaubt Ihnen, den Auftrag zu validieren und zu bepreisen, bevor er in den Workflow eintritt.
</Note>

## Ausgehend — Druma sendet Ereignisse an den Kunden

<Steps>
  <Step title="Ausgehend aktivieren">
    Aktivieren Sie **Ausgehenden Webhook aktivieren**.
  </Step>
  <Step title="Die Webhook-URL eingeben">
    Fügen Sie die **Webhook-URL** des Kunden ein — den Endpunkt in seinem System, der Ereignisse empfängt.
  </Step>
  <Step title="Einen Authentifizierungstyp wählen">
    Wählen Sie eine der vier Optionen für **Auth-Typ**:

    - **Keine** — kein Authentifizierungsheader (nur in vertrauenswürdigen privaten Netzwerken verwenden)
    - **Bearer-Token** — Druma fügt jeder Anfrage `Authorization: Bearer <Wert>` hinzu
    - **Basic Auth** — Druma fügt einen `Authorization: Basic`-Header mit base64-kodiertem Benutzernamen und Passwort hinzu
    - **HMAC-Signatur** — Druma signiert den Body jeder Anfrage mit einem gemeinsamen Geheimnis und sendet die Signatur im Header `X-Druma-Signature` (`sha256=<hex>` des rohen Bodys) sowie, als Replay-Schutz, in `X-Druma-Signature-V2` (`t=<Unix-Sekunden>,v1=<hex>`, signiert über `<t>.<Body>`); der Kunde prüft sie vor der Verarbeitung. Ein Prüfbeispiel steht unter [API-Versionierung](/de/integrations/api-versioning)

    Füllen Sie die Zugangsdaten für den gewählten Typ aus.
  </Step>
  <Step title="Ereignisse zum Senden auswählen">
    Haken Sie die Ereignisse an, die Druma senden soll:

    - **Auftrag erstellt** — ausgelöst, wenn ein neuer Auftrag in Druma bestätigt wird
    - **Status aktualisiert** — ausgelöst bei jeder Statusänderung (zugewiesen, bei Abholung, unterwegs usw.)
    - **Geliefert** — ausgelöst, wenn der Auftrag den Status Geliefert erreicht
    - **Rechnung gesendet** — ausgelöst, wenn eine Verkaufsrechnung an den Kunden gesendet wird
  </Step>
  <Step title="Ausgehende Feldzuordnungen konfigurieren (optional)">
    Erwartet das System des Kunden andere Feldnamen im Payload, verwenden Sie die Tabelle **Feldzuordnung** auf der ausgehenden Seite (identische Bedienung wie eingehend), um Drumas Ausgabefelder vor dem Senden umzubenennen.
  </Step>
  <Step title="Speichern">
    Klicken Sie auf **Speichern**. Druma beginnt ab diesem Zeitpunkt, Ereignisse für die ausgewählten Trigger zuzustellen.
  </Step>
</Steps>

## Feldzuordnung erklärt

Feldzuordnung ist eine Schlüssel-Wert-Übersetzungstabelle. Sie ändert nicht die Daten — nur die Feldnamen im Payload.

**Beispiel — eingehende Zuordnung:**

| Kundenfeld | Druma-Feld |
|---|---|
| `shipment_id` | `reference` |
| `pickup_city` | `pickup_address` |
| `drop_city` | `delivery_address` |
| `cargo_weight_kg` | `weight_kg` |

Mit dieser Zuordnung kann der Kunde seine native JSON-Struktur per POST senden, und Druma interpretiert sie korrekt, ohne dass der Kunde sein Payload umformatieren muss.

**Beispiel — ausgehende Zuordnung:**

| Druma-Feld | Kundenfeld |
|---|---|
| `order_id` | `druma_ref` |
| `status` | `shipment_status` |
| `actual_delivery_at` | `actual_delivery_datetime` |

Nicht zugeordnete Felder werden mit Drumas Standard-Feldnamen durchgereicht.

## Ein Token rotieren

Wird ein Token kompromittiert oder verlässt eine Schlüsselperson das Team des Kunden:

1. Klicken Sie im Tab **API** auf **Token rotieren**.
2. Das alte Token wird sofort ungültig.
3. Das neue Token wird einmalig angezeigt — kopieren und verteilen Sie es, bevor Sie wegnavigieren.

Aktualisieren Sie das Token im System des Kunden so schnell wie möglich. Anfragen mit dem alten Token werden ab Abschluss der Rotation mit `401 Unauthorized` abgelehnt.

---

## Aktivitätszeitstempel

Wurde die API genutzt, zeigt der Tab:

- **Letzter Eingang** — Zeitstempel des zuletzt vom Kunden empfangenen Auftrags
- **Letzter Ausgang** — Zeitstempel des zuletzt an den Webhook des Kunden zugestellten Ereignisses

Diese Zeitstempel sind nützlich, um zu bestätigen, dass die Integration aktiv ist, und um Kommunikationslücken zu diagnostizieren.

---

## Ratenlimits

Druma erzwingt ein Limit von **200 API-Aufrufen pro Stunde pro Kundenkonfiguration**. Anfragen, die dieses Limit überschreiten, erhalten eine `429 Too Many Requests`-Antwort. Das Limit setzt sich in einem rollierenden Einstundenfenster zurück.

Benötigt ein Kunde legitim höheren Durchsatz, kontaktieren Sie den Druma-Support.

<Warning>
Teilen Sie das Bearer-Token eines Kunden nicht mit anderen Kunden und betten Sie es nicht in öffentlich zugänglichen Code ein. Jedes Token gewährt volle eingehende Auftragserstellungsrechte für den Unternehmensbereich dieses Kunden.
</Warning>

Jedes Ereignis enthält außerdem `api_version` und `event_id` (bei Wiederholungen gleich, zum Ignorieren von Duplikaten) sowie die Header `X-Druma-Event-Id`, `X-Druma-Event-Type` und `X-Druma-Timestamp`. `api_version` und `event_id` sind reservierte Schlüssel: Verwenden Sie sie nicht als Ziele der ausgehenden Feldzuordnung. Siehe [API-Versionierung](/de/integrations/api-versioning).

## Formate, die der Kunde senden kann

Das System eines Kunden muss kein JSON sprechen. Druma liest diese eingehenden Formate und wandelt alle in denselben Auftrag um:

| Format | Typischer Absender | Hinweise |
|---|---|---|
| **JSON** | Modernes ERP / TMS | Der Standard. |
| **XML** | SAP IDoc (zum Beispiel Sendungs- oder Lieferungs-IDocs) | Einfaches XML ohne `DOCTYPE`. Ein IDoc pro Anfrage. |
| **EDIFACT** | Verlader mit EDI (zum Beispiel Transportaufträge IFTMIN) | Eine Nachricht pro Anfrage. |
| **CSV** | Verlader, die nur eine Tabelle exportieren können | `Content-Type: text/csv` oder die Verbindung auf CSV festlegen. UTF-8 oder windows-1250, Trennzeichen `,` `;` oder Tabulator, bis zu 500 Zeilen und 200 Spalten. **Eine Datei ist ein Auftrag**: Zeilen werden zu Stopps. |

Druma erkennt JSON, XML und EDIFACT am Inhalt. CSV wird nie erraten: Legen Sie das Format der Verbindung auf **CSV** fest oder lassen Sie den Kunden `Content-Type: text/csv` senden. Der Anfragetext ist auf 256 KB begrenzt. Eine Anfrage mit mehr als einer Nachricht (mehrere IDocs, mehrere `UNH`-Segmente oder ein CSV mit mehreren verschiedenen Auftragsnummern) wird mit `422` und `{"error":"multi_message_not_supported"}` abgelehnt.

<Note>
Vorgefertigte Zuordnungen für bekannte Formate (SAP IDoc, EDIFACT IFTMIN, SAP-Frachtaufträge, Trans.eu-Aufträge) basieren auf öffentlich veröffentlichten Beispielnachrichten. Sie sind mit **Aus öffentlichem Beispiel erstellt** gekennzeichnet, bis eine echte Nachricht Ihres Kunden sie bestätigt (**Mit Kundennachricht verifiziert**). Solange eine Verbindung noch in der Einrichtung ist, wendet Druma eine solche Zuordnung ohne KI-Schritt an; Sie testen sie vor dem Livegang trotzdem mit der Nachricht des Kunden. Passt keine vorgefertigte Zuordnung, schlägt die KI wie bisher eine vor.
</Note>

### Ergänzungen im Assistenten

- **Formatfixierung** — erzwingt den Parser auf JSON, XML, EDIFACT oder CSV, wenn der Kunde immer ein Format sendet.
- **Chip für bekanntes Format** — zeigt, welche vorgefertigte Zuordnung verwendet wird, und ihre Revision. Eine Verbindung bleibt auf der Revision, mit der sie freigegeben wurde; gibt es eine neuere Revision, erscheint die Aufforderung **Zuordnung aktualisieren**, und nichts ändert sich, bevor Sie klicken. Die vorherige Zuordnung bleibt im Versionsverlauf für ein Zurücksetzen.
- **Nachrichtenprotokoll** — die letzten 50 echten Nachrichten mit Format, Ergebnis, wiederholt oder nicht, Idempotenzschlüssel, Dauer und dem, was fehlte; filterbar nach erstellt, von KI erstellt, abgelehnt und wiederholt.

## Dieselbe Nachricht zweimal senden (Idempotenz)

Kundensysteme wiederholen Anfragen. Damit eine Wiederholung sicher ist, fügt der Kunde den Header `Idempotency-Key` hinzu (bis zu 255 Zeichen). Trägt das Format bereits eine eindeutige Nachrichten-ID, kann Druma diese stattdessen verwenden (eine Zuordnung kann sie als Idempotenzschlüssel lesen). **Ohne Schlüssel gibt es keine Duplikaterkennung.**

| Situation | Antwort von Druma |
|---|---|
| Erste Anfrage mit neuem Schlüssel | `200`, der Auftrag wird angelegt |
| Derselbe Schlüssel, derselbe Inhalt, erste Anfrage abgeschlossen | `200` mit dem ursprünglichen `order_id` und `order_number`, dem aktuellen `status` des Auftrags und dem Antwort-Header `Idempotent-Replayed: true`. Kein zweiter Auftrag. |
| Derselbe Schlüssel, während die erste Anfrage noch läuft | `409` `{"error":"in_progress"}` mit `Retry-After: 5`. Später mit demselben Schlüssel erneut versuchen. |
| Derselbe Schlüssel, anderer Inhalt | `422` `{"error":"idempotency_key_reused"}`. Ein Schlüssel bezeichnet genau eine Nachricht. |

Schlüssel werden 90 Tage gemerkt. Eine mit `422` abgelehnte Anfrage hinterlässt keinen Schlüssel, derselbe Schlüssel kann also nach der Korrektur der Daten erneut verwendet werden.

Die `200`-Antwort der eingehenden API enthält jetzt auch das Feld `outcome` (zum Beispiel `created`, `applied_draft`, `parked`, `cancelled_draft`, `ignored_terminal`, `ignored_stale`, `unchanged`, `duplicate_external_id`, `not_found`). Behandeln Sie es als offene Liste: Es können neue Werte hinzukommen. `status` kann `pending` statt `draft` sein, wenn Sie für diese Verbindung unter Einstellungen → Integrationen das Überspringen des Entwurfs aktiviert haben.

## Einen Auftrag ersetzen und stornieren

Liest die Zuordnung eine `message_function` (`original`, `replace` oder `cancel`; leer bedeutet `original`) und die eigene Auftrags-ID des Kunden als `external_id`, ändert eine spätere Nachricht den von ihr angelegten Auftrag, statt einen zweiten zu erzeugen.

- **Ersetzen oder Stornieren, solange der Auftrag noch ein Entwurf ist**: Der Entwurf wird direkt geändert (oder storniert).
- **Auftrag bereits über den Entwurf hinaus** (geplant, unterwegs): Es wird nichts automatisch geändert. Die Änderung wird für einen Disponenten **zurückgestellt**, der eine Aufgabe und eine Benachrichtigung erhält und sie am Auftrag übernimmt oder verwirft.
- **Nach Ablehnung der Ladung oder bei einem abgeschlossenen Auftrag** (storniert, geliefert, fakturiert): Die Nachricht wird ignoriert und der Betreiber informiert.
- Eine Nachricht, die älter ist als die zuletzt verarbeitete für dieselbe `external_id`, wird als veraltet ignoriert; eine identische Wiederholung antwortet `unchanged`.
- Eine unbekannte `external_id` antwortet `200` mit `outcome: not_found`; ein Ersetzen oder Stornieren legt nie einen Auftrag an. Ersetzen und Stornieren benötigen die `external_id`, sonst lautet die Antwort `422` `{"error":"external_id_required"}`.

## Ausgehend im eigenen Format des Kunden

Standardmäßig sendet Druma seinen Standard-Ereignistext als JSON. Für Kunden mit SAP, S/4HANA oder EDI können Sie eine Verbindung im Bereich **Ausgehende Zuordnung** des API-Tabs auf ein **eigenes Ausgangsformat** umstellen:

1. **Wählen Sie eine Vorlage** (EDIFACT IFTSTA D.01B oder D.96A, SAP-IDoc-Sendungsstatus, S/4HANA-/Transportation-Management-Auftragsereignisse als JSON) **oder fügen Sie die vom Kunden erwartete Nachricht ein** und lassen Sie die KI die Zuordnung vorschlagen. Vorlagen basieren auf öffentlichen Beispielen und gelten als nicht verifiziert, bis ein Kunde sie bestätigt.
2. **Tragen Sie die Parteien ein** (Kennungen von Absender und Empfänger) — sie sind immer Ihre eigenen, nie geraten.
3. **Füllen Sie die Statustabelle**: eine Zeile je Druma-Ereignis mit Statuscode und Qualifier des Kunden. **Ein Ereignis ohne Zeile wird nicht gesendet** (es erscheint als *übersprungen*, nichts wird wiederholt).
4. **Vorschau** mit einem echten Auftrag dieses Kunden — es wird nichts gesendet oder gespeichert.
5. Speichern. **Standard-Webhook verwenden** bringt Sie jederzeit zum einfachen JSON-Text zurück.

Die Signatur (HMAC) deckt genau die gesendeten Bytes ab. Eine Zuordnung kann nur einen festen Satz an Auftrags-, Stopp-, Kennzeichen-, POD- und Referenzfeldern nutzen: Fahrernamen, Telefonnummern, Positionen und Preise verlassen Druma dadurch nie.

### Weitere Ereignisse (optional)

Haken Sie sie unter **Zu sendende Ereignisse auswählen** an. Sie werden für eine bestehende Verbindung nie von selbst aktiviert.

- **Stopp-Ereignisse** — `stop.arrived.loading`, `stop.departed.loading`, `stop.arrived.offloading`, `stop.departed.offloading`: die erste erfasste Ankunft oder Abfahrt an einem Be- oder Entladestopp.
- **Auftrag abgelehnt** — `order.declined`: Sie haben eine eingehende Ladung abgelehnt; der Text enthält den Grundcode (`capacity`, `price`, `lane`, `timing`, `equipment`, `other`) und einen optionalen Kommentar.
- **POD hochgeladen** — `order.pod_uploaded`: wird **erst gesendet, nachdem ein Disponent die Dokumente freigegeben hat**. Am Auftrag sendet **POD freigeben und Kunden benachrichtigen** es einmal pro Auftrag; ein von einem Fahrer hochgeladenes Foto löst es nie aus.

Jedes Auftrags- und Stopp-Ereignis liefert außerdem die **Referenzen** des Kunden zurück (zum Beispiel die SAP-Liefernummer, die er gesendet hat), in einem Objekt `references` — nur Referenzen, die für den Kunden sichtbar markiert sind. Der Schlüssel fehlt, wenn der Auftrag keine hat.

### OAuth2 client credentials

Für Gateways, die ein Token verlangen (SAP BTP, Azure AD, Keycloak), wählen Sie den Authentifizierungstyp **OAuth2 (client credentials)** und geben Token-URL (https, öffentlicher Host), Client-ID und Client-Secret ein, optional Scope, Audience und die Client-Authentifizierung (HTTP-Basic-Header oder Anfragetext). Druma holt ein Zugriffstoken, hält es nur im Arbeitsspeicher bis kurz vor Ablauf, wiederholt bei `401` einmal mit einem frischen Token und speichert es nie. Die Zugangsdaten liegen im Tresor, sind nur schreibbar (ein leeres Feld behält den gespeicherten Wert) und werden nie wieder angezeigt.
