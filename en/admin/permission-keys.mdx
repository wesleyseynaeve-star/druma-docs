Use this page when you build a custom role in Settings → Users → Roles. Each permission lists the exact access it gives, where Druma checks it, and which built-in roles hold it by default. The page is generated from the same configuration the app runs on, so it cannot drift from what the app does.

## How to read an entry

Held by default lists the built-in roles that have the permission. In the role builder says whether a company admin can tick it in a custom role. Enforced in says whether the check happens in the app screens, in the database, or both: a permission checked only in the app hides buttons but does not stop a direct call, and one that nothing checks yet changes nothing. Also needs lists permissions that are only useful together.

## Orders

Creating, editing, and deleting orders, plus order notes and pricing fields.

### View orders

`orders:read`

- **Held by default:** Admin, Company Admin, Key User, Planner, Dispatcher, Customer Service, Reporting, Sales
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Opens Operations: the order list, order detail, forwarding and everything shown on an order (legs, stops, references, documents, communications, pallets, templates, e-Transport assignments, status events). Also feeds global search and the sidebar badge counts.

**Where it is enforced.** The Operations section and its routes ask for it; the database uses it as the row-level read gate on orders and roughly a hundred order-related tables (order_legs, order_references, order_tasks, order_communications, templates, goods lines, status events and more). It does not allow any change.

### Create orders

`orders:create`

- **Held by default:** Admin, Company Admin, Key User, Planner, Customer Service, Sales
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database
- **Also needs:** `orders:read`, `commercial:manage`

**What it grants.** Create new orders: the New order action, copying an order, creating several orders from a spec, scanning an order document, and creating orders from templates (including scheduled template runs).

**Where it is enforced.** Both, but in two layers. The screens and the RPCs/Edge Functions behind them (next_order_number, copy_order, create_orders_from_spec, instantiate_order_template, document-scan, order-template-scheduler) check this key. The INSERT into the orders table itself is checked against the database key commercial:manage, which the role builder offers as a database permission: a custom role holding orders:create but not commercial:manage is stopped at that insert.

### Edit orders

`orders:edit`

- **Held by default:** Admin, Company Admin, Key User, Planner, Customer Service
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database
- **Also needs:** `orders:read`, `commercial:manage`

**What it grants.** Change existing orders in the places the app lets you edit them: order drawers, subcontracting and carrier assignment, groupage and forwarding panels, VAT and extras, cancelling a sold or subcontracted order, resolving eCMR exceptions and automation jobs, handling client delay notices, approving or rejecting platform proof-of-delivery, e-Transport vehicle change and GPS pause actions.

**Where it is enforced.** Screens ask for it, and about fifty RPCs check it (cancel_subcontractor, cancel_sell_order, dissolve_groupage, set_preloaded_trailer, resolve_ecmr_exception, approve_transporeon_pod, write_off_remainder and others), as do the transporeon-api, inbound-order-email and client-api-admin Edge Functions. The UPDATE on the orders row itself is checked against commercial:manage (a database permission the role builder offers): a custom role needs both.

### Delete orders

`orders:delete`

- **Held by default:** Admin, Company Admin, Key User, Planner, Customer Service, Sales
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database
- **Also needs:** `orders:read`, `commercial:manage`

**What it grants.** Move an order into the deleted state: the Delete / Discard buttons on the order list, the intake workbench (single and bulk) and the planning board, and the clean-up of a placeholder order after linking or saving.

**Where it is enforced.** Screens hide the delete controls without it. In the database the trigger trg_orders_soft_delete_needs_permission refuses an authenticated user who sets orders.deleted_at without it (42501 order_delete_needs_permission); the orders DELETE policy needs it together with commercial:manage. System paths (correction reverts, cron, service role, other SECURITY DEFINER functions) are not affected. Restoring a deleted order stays under the normal update rule.

### Add order notes

`orders:notes`

- **Held by default:** Admin, Company Admin, Key User, Planner, Dispatcher, Customer Service, Reporting, Sales
- **In the role builder:** Can be ticked
- **Enforced in:** Database and server functions

**What it grants.** Read and add internal order notes, and let Ask Druma read them.

**Where it is enforced.** The order_notes table (SELECT and INSERT policies) and the Ask Druma notes tool check it. No screen hides notes on its own.

### View/edit agreed price

`orders:agreed_price`

- **Held by default:** Admin, Company Admin, Key User, Planner, Customer Service, Reporting, Sales
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** See and edit the price agreed with the client on an order, on templates, in the Pricing views and in revenue analytics.

**Where it is enforced.** Screens check it; the trigger enforce_orders_financial_column_permissions blocks writing the agreed-price columns without it; create_orders_from_spec, copy_order, template RPCs and the revenue analytics RPCs check it; the order-price-apply and order-template-scheduler Edge Functions check it.

### View/edit invoice status

`orders:invoice_status`

- **Held by default:** Admin, Company Admin, Key User, Planner, Customer Service, Reporting
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database
- **Also needs:** `orders:edit`

**What it grants.** Edit the invoice status and VAT section of an order.

**Where it is enforced.** The order VAT section is editable only with orders:edit and this key together; the trigger enforce_orders_financial_column_permissions blocks changing the invoice-status columns without it.

### View own orders

`orders:read_own`

- **Held by default:** Driver, Client
- **In the role builder:** Can be ticked
- **Enforced in:** App screens only

**What it grants.** The driver or client sees only the orders that belong to them (their own loads or shipments).

**Where it is enforced.** App marker only: the app uses it to recognise accounts that have no office read access (for example roster-only mode). Row access for drivers is enforced by the orders SELECT policy through driver assignment, not by this key. Exempt from the grant ceiling.

### Correct truck/trailer/driver assignment

`orders:correct_assignment`

- **Held by default:** Admin, Company Admin, Key User
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database
- **Also needs:** `data:correct`

**What it grants.** Retroactively correct the truck, trailer and driver on a past leg, insert or remove relays, void or add stops, resequence stops, reopen a leg, correct terminal status, e-Transport UIT, subcontract carrier and rate, and groupage run assignment: the correction workspace of the Key User hub.

**Where it is enforced.** The correction workspace and planning-board correct-assignment dialogs check it; the correct_* RPCs and _assignment_correction_can_correct check it in the database, usually together with data:correct, a reason and the correctable-fields catalogue.

### Override credit stop

`orders:override_credit_stop`

- **Held by default:** Admin, Company Admin, Key User, Planner
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Release an order that the client credit-stop guard blocked (override for a single order).

**Where it is enforced.** The credit-stop override modal checks it; the RPC override_client_credit_stop checks it and records the override.

### Override a trailer equipment mismatch

`orders:override_equipment`

- **Held by default:** Admin, Company Admin, Key User, Planner
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Assign a trailer that fails the order equipment requirement (tail lift, ADR, temperature and so on) anyway, with the mismatch recorded.

**Where it is enforced.** The confirm-assignment sheet shows the override only with it; override_equipment_mismatch checks it and writes equipment_overrides.

### Override a driver language mismatch

`orders:override_language`

- **Held by default:** Admin, Company Admin, Key User, Planner
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Assign a crew that does not speak the order required language anyway, with the mismatch recorded.

**Where it is enforced.** The confirm-assignment sheet shows the override only with it; override_language_mismatch checks it and writes language_overrides.

### Correct data on closed records

`data:correct`

- **Held by default:** Admin, Company Admin, Key User
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Open the Key User hub and correct allow-listed fields on records the normal workflow no longer exposes (closed trips, delivered orders, invoices, payments, expense decisions), with a mandatory reason and a full audit trail; also resolve key-user fix requests.

**Where it is enforced.** The Key User route, the closed-record lock host and the correction dialogs ask for it; apply_data_correction, correction_impact_preflight, revert_correction, resolve_key_user_request and some forty correct_* / reverse_* RPCs check it, and the key alone grants nothing: the (entity, column) pair must be in the correctable_fields catalogue and a reason is required.

### Escalate an order to the planner

`orders:escalate`

- **Held by default:** Admin, Company Admin, Planner, Dispatcher, Customer Service
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Escalate an order to the planner, and use the gap-coverage queue and truck-coverage views (trucks without a reload). Holders also receive the "trucks without reload" reload alerts.

**Where it is enforced.** App for the screens (mobile nav, Coverage queue, customer-service mobile model); the database uses it to pick the recipients of the trucks-without-reload notification (notify_trucks_without_reload, via company_users_with_permission).

### Resolve an order escalation

`orders:escalation_resolve`

- **Held by default:** Admin, Company Admin, Planner, Dispatcher
- **In the role builder:** Can be ticked
- **Enforced in:** Database and server functions

**What it grants.** Resolve an order escalation. Holders are also the recipients of escalation notifications.

**Where it is enforced.** Database only, and only as a recipient rule: the escalation notification is sent to users holding this key (company_users_with_permission). It is not a screen or write gate.

### Write orders, clients, quotes and subcontractors

`commercial:manage`

- **Held by default:** Admin, Company Admin, Key User, Planner, Customer Service, Sales
- **In the role builder:** Can be ticked
- **Enforced in:** Database and server functions

**What it grants.** The commercial write set: create, edit and delete orders (with legs, stops, extras and goods), clients and their contacts, quotes, tenders, subcontractors and their documents, CRM contacts and deals, capacity contracts, client instructions, groupage orders and handling units; read price lists and rate cards.

**Where it is enforced.** Database only (policies on dozens of tables, notably the INSERT/UPDATE/DELETE policies of orders, clients, quotes, tenders and subcontractors, and several RPCs and Edge Functions such as client-portal-token). The role builder offers it as a database permission (DRUMA-1595): a custom role needs it, in addition to orders:create, orders:edit or clients:manage, to write these tables.

## Planning Board

The planning board and live map used to assign orders to trucks.

### View planning board

`board:read`

- **Held by default:** Admin, Company Admin, Key User, Planner, Dispatcher
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Opens the planning board and the groupage consolidation pages; reads board signals, auto-plan runs and suggestions, language requirements and overrides, and AI agent settings shown on the board.

**Where it is enforced.** Screens ask for it; the database uses it as the SELECT gate on auto_plan_runs, auto_plan_suggestions, company_board_signals, groupage_consolidation_runs and suggestions, language_requirements, language_overrides, and as the gate of board_bootstrap_aux and resolve_language_requirements.

### View live map

`map:read`

- **Held by default:** Admin, Company Admin, Key User, Planner, Dispatcher, Fleet Manager, Customer Service, Mechanic, Resource planner, Reporting, Sales
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database
- **Also needs:** `orders:read`, `fleet:operate`

**What it grants.** Opens the Live Map under Dispatching, and every in-app "open on map" link. Without it the Live Map menu entry is hidden and the route shows a no-access page.

**Where it is enforced.** The Dispatching navigation, the Live Map route and the map links ask for it. The database requires it for the live_map company snapshot, together with orders:read and fleet:operate; the underlying tables stay governed by orders:read and the fleet keys.

### Assign orders on the board

`board:assign`

- **Held by default:** Admin, Company Admin, Key User, Planner
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Assign orders to trucks, drivers and trailers on the board, including pre-plans, and handle planning problems.

**Where it is enforced.** The board assignment actions and Problems tab ask for it; the database uses it on order_preplans (full access) and in _roster_apply_order_effects. The write to the order row itself still runs through the orders policies.

### Run consolidation suggestions

`groupage:suggest`

- **Held by default:** Admin, Company Admin, Key User, Planner, Dispatcher, Fleet Manager
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Run "Suggest consolidations" on demand in groupage (spends metered PTV routing for the company).

**Where it is enforced.** The groupage auto-consolidation panel asks for it; the groupage-suggest Edge Function checks it server-side; the database also uses it for read access on the consolidation, groupage order, route, stop and handling-unit tables and for updating groupage routes.

### Confirm/decline a pending dispatch assignment

`dispatch:confirm`

- **Held by default:** Admin, Company Admin, Dispatcher
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Accept or decline a pending dispatch assignment, force or mark handled client delay notices, resolve dispatch issues and change dispatch settings.

**Where it is enforced.** Dispatch screens and gates ask for it; confirm_order_dispatch, decline_order_dispatch, compute_dispatch_status_for_write, dispatch_settings_update, dispatch_resolve_issue and the nav badge counters check it; the dispatch-send Edge Function checks it. Planners can see the queue but cannot confirm on a dispatcher behalf unless granted this key.

### Read the company-wide default settings

- **Enforced in:** Database and server functions

**What it grants.** Read the global company-wide default settings row (cost-per-km and similar fallbacks).

**Where it is enforced.** The SELECT policy on the singleton company_config table asks for it (via user_company_ids_with_permission). No screen checks it directly.

## Fleet

Trucks, trailers, and fleet records.

### View fleet

`fleet:read`

- **Held by default:** Admin, Company Admin, Key User, Planner, Dispatcher, Fleet Manager, Reporting
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Opens the Fleet and Drivers sections: trucks, trailers, documents, fuel, driver list, performance, tacho archive; reads fuel fills, tyres, defects, incident reports, positions history and driver absences and shifts; feeds fleet analytics.

**Where it is enforced.** Section routes and nav ask for it; about fifty SELECT policies (tyres, fuel_fills, defect_tickets, post_trip_inspections, vehicle_position_history, driver_shifts, fleet_groups and others) and the fleet and fuel analytics RPCs check it. Driver-score views additionally need the database key reports:driver_data.

### View driver roster

`roster:read`

- **Held by default:** Admin, Company Admin, Key User, Planner, Dispatcher, Fleet Manager, Resource planner
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** See the Driver Roster (the schedule carries sickness codes, which are special-category data). Opens the Drivers section even without fleet:read.

**Where it is enforced.** The roster tab and route guard ask for it; the SELECT policies on driver_roster_days, roster_bases, roster_base_defaults and roster_order_effects and the roster helper RPCs check it.

### View workshop

`workshop:read`

- **Held by default:** Admin, Company Admin, Key User, Planner, Dispatcher, Fleet Manager, Mechanic, Reporting
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

**What it grants.** Opens the Workshop section: board, work orders, defects, damage, maintenance and tyres; reads jobs, tasks, attachments, time logs, parts and quantities, stock levels (not costs), tyre records and incident reports.

**Where it is enforced.** The Workshop route and nav ask for it; about twenty SELECT policies (work_orders, work_order_tasks, parts, stock_levels, tyres, maintenance_plans, defect_tickets and others) and the workshop_* read RPCs check it.

### Manage fleet

`fleet:manage`

- **Held by default:** Admin, Company Admin, Key User, Fleet Manager
- **In the role builder:** Can be ticked
- **Enforced in:** App screens and database

## Database-tier permissions

These permissions name a row-level security role-set in the database. Unless marked as selectable they cannot be given to a custom role, so a custom role without them cannot write the tables they protect, even with the matching application permission ticked.

### capi_library:manage

`capi_library:manage`

- **Held by default:** Admin
- **In the role builder:** Not selectable
- **Enforced in:** Database and server functions

**What it grants.** Druma staff only: edit the shared known-format library that recognises client order messages (SAP IDoc, EDIFACT, JSON freight orders), publish revisions and mark them verified.

**Where it is enforced.** The capi_library_* functions and the capi-library-admin Edge Function check it; the library tables have no tenant policy. Held by the platform admin alone, never grantable by a company admin.
